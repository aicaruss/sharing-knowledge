The whole video in seven points

  1. The premise: the model has no memory at all. Anything that looks like recall — ChatGPT knowing your name, a coding agent knowing your repo — is a memory system somebody built around the model. Memory is an architecture decision, not a model feature.
  2. Three questions, in this order: what is a memory (text, a table, or a graph) · how does the agent find it (do nothing, keyword, RAG, Graph RAG) · how do you maintain it (add, delete, overwrite, noop, retire, attribute, reflect). Nearly every product argument is really an argument inside one of those three boxes.
  3. The first retrieval strategy is no retrieval. If the memory file is short, it is simply preloaded into the context window — which is exactly what his own harness and the Hermes harness do. No embeddings anywhere. He says this out loud in the first two minutes, against the RAG / agentic-RAG / Graph-RAG discourse.
  4. Maintenance is where the design lives. Deleting a superseded fact destroys history; retiring it — bounding the old value with a time range and adding the new one — keeps the trail you need to explain an answer later. His example is his own repo: 1,000 stars on day 25, 1,300 on day 26.
  5. Five layers, concretely: plain text files → SQLite state.db with keyword search → vector stores → mem0 (row memory and graph memory, both stored as vectors) → Zep (a temporal graph with validity windows). Plus LangMem, which is a package, not a store.
  6. He races four contenders on a dinner party — SQLite, mem0 and Zep from that list, plus LangMem — on four seeded facts, against a no-memory control. Plain text is not entered and the vector store is never tested. The sharpest design choice in the test: a control group with no memory at all, which passes a question by correctly reporting that it has no record. Sophistication does not win. Local SQLite answers in 4.6s; the temporal graph spends most of the demo seeding.
  7. The conclusion: the harness is flexible and replaceable, so the memories are the asset — and you should pick the simplest layer your use case actually needs. The graph did produce one genuinely valuable thing, an edge labelled "revealed ending of", and he still calls it possible overkill for smaller use cases.
Read the comparison with four things in mind

1. The author's position. Shen Sean Chen wrote Waku Agent, the open-source harness the arena runs inside, and the plain-text approach the video ends up favouring is his own project's approach. That does not make the argument wrong; it does mean the conclusion and the product point the same way.

2. n=1. One run per question, wall-clock timings read off a dashboard, no repetitions and no statistics. Every number below is what he saw once, not a measurement.

3. Not like-for-like. SQLite runs on local disk; mem0, LangMem and Zep are network calls to hosted services. Part of every gap is round-trip latency rather than retrieval quality, and the video does not separate the two.

4. One store and one mode were never tested. The vector store (Supabase PGVector) was left out deliberately — in his words, "because we're not testing embeddings here" (20:01) — and mem0's graph mode sits behind a paid tier he declined to buy. The vector-store row of any comparison here is theory, not result.

0Vocabulary first

The video reuses harness vocabulary from his earlier videos without re-explaining it. These are the terms the rest of this page leans on, defined in his sense rather than the textbook one.

TermWhat it means here
HarnessEverything around the model: the loop, the tools, the tracing, the memory system. His is Waku Agent; he refers throughout to Hermes, another harness with the same plain-text habits.
Working memoryWhat actually gets assembled into the context window for one agent run, drawn from the three memory types below.
Procedural / semantic / episodic memoryHis harness's three retrieval categories: procedural = a skill, a stored procedure that fires on a trigger; semantic = durable facts; episodic = dated events. Note that 0:40 is also the only place he says "pillars", and he means these three; the "pillar 1/2/3" labels used on this page follow the video's own chapter titles, which apply the word to the what / find / maintain trio.

Embedding / vectorA word or fact turned into a list of numbers so similarity can be computed. He offers "1024 by 1" as an illustrative shape, not a specification.

1Every LLM call starts with amnesia

0:00 – 1:52 · jump to 0:00

The opening is the load-bearing claim of the whole video, and it is worth stating precisely, because a lot of marketing depends on blurring it.

"…any LLM call does not carry any weight for long terms. The reason why your ChatGPT and Claude code remembers what you talked about from the past is because it has already crafted this memory system for their own AI agent harness."

— Shen Sean Chen, 0:03 (from the video's auto-generated caption track)

So "does the model remember me?" is the wrong question. The model never remembers. Somebody chose a place to put the facts, a way to fetch them back, and a policy for what to do when they go stale. Those three choices are the video, and they are the three pillars in the next section.

He then recaps his harness in one breath — an agent loop that calls tools and delegates sub-agents, assembling working memory from procedural, semantic and episodic memory — and notes Hermes builds its memory much the same way. That single line is the seam with the earlier entry in this library: Loop Engineering vs Graph Engineering names the retrieval gate and those three memory types in passing. This video is that line opened up.

Then, unusually early, he plants a flag against the prevailing discourse:

"Retrieval augmented generation has always been there, but there's no retrievals or embeddings in Hermes and Waku agent."

— Shen Sean Chen, 1:02

Two systems people would describe as memory-heavy agents contain no retrieval machinery at all. Hold that thought — it is the answer to pillar 2 arriving before the question.

3Pillar 1 — what a memory actually is

2:31 – 5:04 · three shapes, and where embeddings really sit

Three storage shapes, each shown in a running system rather than described abstractly:

  • Text or markdown. He opens Hermes' .hermes/memory/memory.md on camera — plain text, fed into the context window whenever you ask something. In his own harness the equivalent files sit under .waku, including SOUL.md, the system prompt and personality.
  • Rows in a table. A spreadsheet, a Google Sheet, or a relational database. In Hermes that is state.db, a SQLite file you can open and read the schema of.
  • A graph of nodes and edges. His definition is deliberately plain: a way to build connections between pieces of information. He demonstrates with Zep's relational graph view, walking a small example — a founder called Alex, a Lisbon AI meetup, a robotics startup, a product launch in May and another in June — and points out that the interest is in the interconnections, not the individual facts.

Then the question a RAG-shaped audience will already be shouting, and the answer that makes the framework coherent:

Embeddings are not a fourth kind of memory

Where does the vector go? Into one of the three shapes above. With Supabase PGVector — the setup he uses himself — the memory is still rows in a table; some of the columns just happen to hold vectors. Or it sits in a NoSQL store. Embeddings are a property of how you search, not a separate thing to be. That is why they belong to pillar 2, not pillar 1.

4Pillar 2 — how the agent finds it, starting with "do nothing"

5:04 – 7:29 · jump to 5:04

Four strategies, and the ordering is the argument: the cheapest one is not searching at all.

The first lane is the one worth arguing with. "Do nothing" is not laziness; it is a claim that for a small enough memory the context window is the retrieval system, and that anything else adds a component that can be wrong. The cost is equally plain: it does not scale, and everything you preload competes for the same window.

5Pillar 3 — maintenance, where the real design lives

7:29 – 9:47 · jump to 7:29

He announces four ways to maintain a memory system and then delivers a decision set plus two named practices — the count does not quite line up, and I have kept his groups rather than tidying them:

1 The decision, on every new fact — add · delete · overwrite · noop (do nothing) · retire.

2 Attribute — record where the fact came from: the user talking to the agent, a web search, a calendar lookup. "In human language… tracing where the source comes from."

3 Reflect — drop or merge duplicates and stale facts, as a scheduled pass rather than in the moment.

Retire, not delete — the 1,000 → 1,300 stars example

This is the part of the video I would keep if I could keep one paragraph. His own repo had 1,000 stars in its first 25 days. On day 26 he tells the agent it now has 1,300. The naive move is to overwrite the old number, because the old number is wrong now. His argument is that the old number is not wrong — it was true then, and the fact that growth jumped 30% in one day is only visible if both values survive.

Attribute, and then reflect — including Anthropic's "dreaming"

Attribute is one line in the video and cheap to implement: store the provenance of each fact — user, web search, calendar. It is the difference between "the agent believes X" and "the agent believes X because the user said so on Tuesday".

Reflect he admits overlaps with delete and retire, and then attaches it to a bigger idea:

"…reflect sometimes can link to what Anthropic has proposed, which is dreaming. Dreaming happens when we are not working."

— Shen Sean Chen, 9:12

The mechanism he describes: while the agent is running it is busy accumulating — facts, dated events, procedures turning into skills. When it is idle, schedule a pass that reflects over the pile, merges duplicates and drops what no longer matters. He calls it a post-mortem or post-process step for the memory system.

This citation cannot be followed up as given

"Dreaming" is attributed to Anthropic with no paper, author, title or link anywhere in the video. It is recorded here as he presents it, and it is not citable in that form — if you want to use the idea, you will need to find the primary source yourself.

6The five layers, concretely

9:47 – 18:16 · jump to 9:47

Each layer gets the same three questions: what is the memory, how is it found, how is it maintained.

Layer 1 — plain text (Hermes, Waku Agent)

Three files doing three different jobs. SOUL.md is the system prompt and personality — he opens his own Hermes SOUL to show that it is configured to talk like Pikachu, with "Pikapi" reserved for addressing him directly, and points out you can edit it to anything. Skills are procedures, loaded by trigger — the one he describes researches all the AI agent videos on the internet and then reports each morning on the latest news the channel should cover in its next video (paraphrase of 10:42). memory.md holds durable facts that accumulate as you talk. All three are files you can open and edit by hand.

Layer 2 — SQLite state.db, and the consolidation pipeline

Rows in a relational database, found with FTS5 keyword search, maintained either by editing it yourself or by letting the harness consolidate. Consolidation is the mechanism worth stealing regardless of which layer you pick: every conversation turn is saved into state.db, and every five or ten turns cheaper auxiliary models distil that history into durable facts in memory.md. Raw history stays cheap and complete; the expensive context window only ever sees the distillate.

Layer 3 — vector stores (Supabase PGVector, Weaviate, Pinecone)

Memories stored as high-dimensional vectors plus metadata, found by similarity search, maintained by upsert and delete. He notes Supabase is a relational database and "technically not a vector store" — PGVector is the extension that makes it one. His suggestion: give a vector store the same consolidation module he showed for state.db, so maintenance is not just upsert-and-hope. This layer is never raced — see the caveat at the top of the page.

Layer 4 — mem0: row memory and graph memory

Two modes, and he is careful that both are stored as vectors. Row memory is a durable fact per row; he opens one in his own mem0 portal and reads it aloud — a standing fact that a German buyer requires vegan certifications on every SKU they are sold (paraphrase of his reading at 14:59; that screen was never captured, so this is what he says it says). Maintenance is add / update / delete / noop / supersede, and he ties supersede straight back to the stars example. Graph memory is nodes and edges with traversal.

Two admissions in this section are worth more than the feature list:

  • On how retrieval actually happens in the hosted product: "I don't know if they did the keyword search here or doing some embeddings or rags" … "I'm not sure which one they're actually using behind the scene" (15:16–15:26). The open-source project exists, but he is looking at the enterprise version.
  • On graph-mode maintenance: "I'm not too sure if it does supersede maybe it does too." … "For these things you should check the source code." (16:12–16:21)

And the reason graph memory never enters the race: it needs a paid tier he declines to buy, so he goes looking for an alternative — which is how Zep enters.

Layer 5 — Zep: temporal graph memory

Nodes, edges, and validity: a graph that evolves over time. Retrieval is vector search over both nodes and edges plus traversal across the graph. Maintenance is the point — it invalidates with a time range rather than deleting, so, in his framing, "you never delete it but the history survives". This is the pillar-3 idea from section 5 shipped as a product feature.

Plus LangMem — a package, not a store

LangChain's memory library, which he is explicit about: there are no stores of its own. It operates over whatever store you bring, extracting and resolving updates before anything is written. Worth holding onto for the race, where "LangMem has nothing" in the store viewer is not a failure — it is the correct behaviour for a library that does not own storage.

7The dinner party: four contenders, a control group, four facts

18:16 – 26:32 · jump to 18:16

The second half is a live demo of what he calls the arena — a memory-race screen in his own dashboard, whose name the captions render as "memory rays" (18:39). One scenario (planning a dinner party), one set of facts, seeded into every store, then the same questions asked of each. The video's own chapter title for this stretch says "seeding 5 stores", folding the control group in with the stores; this page counts the four contenders and the control separately. The facts as he reads them out:

1 Jensen Huang is coming — and last time, he knocked the chili oil onto the white rug.

2 Elon Musk is coming and said he would arrive at 7:00 — later updated: he cannot get there until 9:00 pm.

3 Tom Holland is on the list — he told the ending of his next film over coffee last Tuesday, and can never keep the secret of an unpublished film.

4 Paul Graham owes 20 quid from a sourdough bet; they met in Lisbon. (He notes "quid" is British for pounds — and one question about it is asked in Chinese.)

The four contenders: SQLite, mem0, LangMem and Zep. Against them, in its own role, Control — an agent with no memory at all. Supabase is deliberately absent.

The control group is the best idea in the test

Control is an agent with no memory at all. It is there to catch the failure mode that makes memory benchmarks worthless: an answer that looks right because the model guessed, or because the fact leaked into the prompt. And note how it passes — not by answering, but by correctly reporting that it has no record. When it is asked when Elon arrives it goes further: it searches memory, uses its tools to check the calendar, and reports there is no such event. A memory system has to beat that, not beat silence.

Same facts, in plain code

While the seeding grinds away he walks examples/memory_native in his repo, one file per store, and the shape is nearly identical each time: a list of facts, a list of questions, a client, then add-per-fact and search. LangMem builds a memory manager and invokes a conversation per fact; mem0 uses client.add then a search; the Supabase example additionally has to embed and then retrieve; Zep, being a graph by default, adds each fact to a graph and queries with client.graph.search. Worth noticing: the code examples use their own smaller fact set (meeting Alex at a Lisbon AI meetup; a launch scheduled for May, then moved to June — superseding again), not the dinner party.

The results

The Chinese question is the most instructive result

Asked in Chinese how much Paul Graham owes, SQLite retrieves the right fact and then answers in English, taking 10.3s. mem0 answers correctly in Chinese, naming the bet and Lisbon. His reading:

"I don't know. Maybe because … SQLite is a little bit too simple for keyword searching, so it doesn't really know how to search in Chinese because the memory was in English."

— Shen Sean Chen, 24:31

Note the hedge — "I don't know. Maybe" — and keep it. It is a plausible mechanism rather than a diagnosis: keyword matching has no way across a language boundary, because the words simply do not overlap, whereas an embedding of the question can land near an English fact with the same meaning. But the observed symptom was the reply language, not a retrieval miss, and the video does not separate "found nothing useful" from "found it and answered in the wrong language". As stated, it is exactly the kind of result worth re-running properly — which is also the honest reading of a single run.

That is the Graph RAG claim from section 4, delivered. Two nodes joined by a bare link would be noise; an edge that has been summarised into "revealed ending of" is a retrievable relationship. Two cautions on this section

The seeding delay is not measured. He loses patience, cuts away twice, and at one point fills time with a community plug — so "taking forever" is a wall-clock impression on one run over a network, not a benchmark. Once seeded, the store answered in 4.9s, 4.9s and 6.4s, which is competitive with everything else.

His reading of the chili-oil edge is unreliable. Late in the video he names the wrong guest for the spill — the seeded fact attributes it to Jensen Huang — so his specific complaint about that edge cannot be taken at face value. What the graph clearly does show is a stain relationship with no guest attached, which is a real gap either way. The slip does not touch the timings or the earlier results.

10What to take away

The closing argument arrives, oddly, in the middle of the video rather than at the end — at 12:13, while he is still on plain text:

"What lasts forever or what matters most to you eventually is the memories. … If you're committing these memories and then store them well and prepare them well and then take care of them, then these memories are the most valuable assets for any AI agent harness."

— Shen Sean Chen, 12:13–12:24

Note the condition, which is easy to lose: the memories are the asset if you commit them, store them well and take care of them — pillar 3 doing the work. Paired with the line just before it — "agent harness is very flexible. You don't have to stick to any standard" (12:06) — the argument is an asymmetry: harnesses get rewritten, models get swapped, frameworks come and go, and the memory has to survive all of it. Which is a good reason to prefer a store you can open, read and edit by hand over one you can only reach through somebody's API.

  • Answer the three questions explicitly for anything you build. Most memory arguments are people answering different pillars at each other.
  • Start at "do nothing". If the facts fit in the context window, preloading a file is not a compromise — it is one fewer component that can be wrong. Climb only when the size or the retrieval quality forces you.
  • Retire, don't delete. Bounding an old fact with a validity window costs almost nothing and preserves the ability to explain an answer you gave last week. This is the one design idea here that applies whatever store you use.
  • Attribute every fact. "The user told me on Tuesday" and "a web search said so" deserve different levels of trust.
  • Always run a control group. An agent with no memory that correctly says "I have no record" is the baseline that stops you crediting a memory layer for the model's guesswork.
  • Buy a temporal graph for the relationships, not the speed. On this evidence the edge summarisation is real and the latency is real; if your use case is small, the video's own conclusion is that it may be overkill.
  • For a regulated or audited setting — the reason to care about pillar 3 is traceability. Retire-plus-attribute is what lets you reconstruct why an agent said something months later; a store that only overwrites cannot do that at any price.
