From Signal to PR:
Anatomy of a Self-Improving Agent

Jason Lopatecki — co-founder, Arize AI

Watch the source talk on YouTube youtube.com/watch?v=9HbzAWnKbo4
Observability Agent skills Traces & evals Sandboxes Self-healing systems

The whole talk in six points

  1. The picture he's selling: instead of getting paged at midnight and starting to dig, you wake up to an issue that has already been investigated — traces pulled, root cause found, and a pull request waiting for review.
  2. The unlock is boring and specific: traces on a filesystem. A skill pulls the relevant production traces and logs down as files into the repo, right next to the code. Sometimes ten megabytes of them. Coding harnesses are magical with files and hopeless with a dashboard.
  3. Why that works: a trace tells the agent the exact code path the software actually took. Without it, the agent is guessing among a million possible branches.
  4. The loop gets inverted: it used to be human investigates → agent helps fix. Now it's agent investigates first → human reviews. Your job moves from responder to reviewer.
  5. The counterintuitive consequence: you should now trace and log ten times more, not less. Humans couldn't dig through that volume — it was just noise. Agents can.
  6. He is honest about the limits: a one-line fix is the easy case. Bigger fixes still need a human to drive. The real win is killing the cold start, not full autonomy.

0Vocabulary first (so the rest reads easily)

TermWhat it means in this talk
TraceA structured record of one request travelling through your system — every step, every call, in order. In an AI system it's usually the agent framework's record of a full run. The single most important artifact in this talk, because it reveals which path the code actually took.
ObservabilityThe discipline of instrumenting a system so you can tell what it's doing from the outside. Traditionally: dashboards, graphs, log searches — all built for a human to look at.
SkillA packaged capability you give a coding agent — instructions plus tooling for a specific job. Here: skills that talk to observability platforms and fetch the right data into the repo.
HarnessThe coding-agent environment doing the work — Claude Code, Cursor, and so on. In this architecture it's a choice you make, not something Arize dictates.
SandboxAn isolated running environment where the agent does its investigation. It's the thing that replaces "the agent runs on my laptop."
EvalAn automated judgement of quality layered on top of traces — often LLM-as-a-judge. Not a replacement for traces; extra pre-processed signal attached to them.

1Where he's coming from: their own agent "frankly sucked"

Lopatecki opens by placing himself as a builder, not just a founder. Arize has an in-product agent called Alyx. His words about the first version, from roughly two years ago when they were first in the space to ship one: it "frankly sucked."

That matters because it frames everything after it. What Arize built into Signal — the subject of this talk — came out of their own daily pain running Alyx in production. He is not describing a theory; he is describing the automation of chores he was already doing by hand.

"You can build at agent speed, but today you can't improve your systems really at that agent speed."

— Jason Lopatecki, around 3:30

That gap is the whole problem statement. Writing software got dramatically faster; diagnosing and repairing it in production did not.

2The core claim: observability stops being a dashboard

His argument is that the observability space is changing massively right now, and he frames it in three eras.

Why traces specifically

He gives the reason in one sentence, and it's the load-bearing sentence of the whole talk: a trace tells you what path in the code it took. Without that, the agent is guessing — and, in his words, "there's a million paths it could have taken."

This is why traces, not dashboards, are the substrate. A dashboard summarises. A trace is a specific, factual record of one actual execution — exactly the kind of thing a coding agent can reason over.

3Inverting the loop

The structural change Arize made to their own workflow is an inversion of who moves first.

His own caveat, stated plainly

"That's the reality of where we are today: there's still — maybe it's not human reviewing but human driving — steps two and three." In other words, the agent reliably owns step one (gathering and investigating). Steps two and three are often still yours. He returns to this later: a one- or two-line fix is the ideal case; the bigger the fix, the more likely a human has to spearhead it over the line.

He also names the real bottleneck, and it isn't code generation. Among people already using coding agents with skills, the bottleneck is confidence: "is this fix the right one to push?"

4The anatomy: what a self-improving agent is made of

He breaks the loop into three parts. This is the structural heart of the talk.

An aside that tells you where the industry is

Mid-talk he polls the room. First: who here has created skills? — a good showing. Then: who has created a skill that interfaces to an observability platform? — his own read of the response was "a handful." That gap is essentially the market he's describing.

5The actual unlock: traces on a filesystem

If you remember one mechanism from this talk, make it this one. It is deliberately unglamorous.

The skills don't hand the agent a dashboard link or an API cursor. They pull the relevant traces and logs down as temp files into the repo — sitting right next to the source code. Sometimes, he says, that means 10-megabyte files sitting in the repo.

Combine that with the repo itself, and the agent now has both halves of the puzzle: what the software actually did (the trace) and the code that did it (the repo). That combination — right data, right file format, sitting alongside the code — is what he calls the magic.

6From your laptop to a sandbox

He points out that many people in the room already do a version of this — locally, by hand. You kick up an agent on your laptop, point it at some data, and let it work. The move he's describing is not a new capability so much as a relocation.

7A real fix: the Alyx "stream canceled" bug

He walks through a concrete case from their own product rather than a hypothetical — which is the most useful part of the talk for calibrating expectations.

  • Alyx, their in-product assistant, manages its task list through a mechanism he calls to-do update.
  • It was calling a bunch of these to-do updates in sequence and erroring out with a stream canceled event.
  • The question they had to answer: how do you assemble the data to debug that — and how do you do it automatically?
  • The result was a one- or two-line fix that the system came up with on its own.
The honest framing

He immediately qualifies it: "these are ideal, but a lot of times the fixes are bigger." And the bigger the fix, the more likely a human ends up spearheading it over the line. What the system reliably removes is the cold start — arriving at the problem with all the information already assembled, then guiding it the rest of the way.

8The counterintuitive part: trace ten times more

This is the recommendation most likely to surprise a platform team, because it reverses years of standard advice about log hygiene and noise reduction.

His reasoning, close to verbatim: before, you wouldn't log that much, because humans can't dig through all the logs — it's just noise. But by logging and tracing an order of magnitude more than we do today, you can create continuous loops that know exactly what path your software took, and can actually fix it.

9The product, and the deployment question

The middle of the talk is a live demo. The useful structural facts:

ProductWhat it is
AXTheir SaaS platform. Can also be deployed into a customer's VPC.
PhoenixThe open-source option — "if you just want to start tomorrow."
SignalThe self-improving agent this talk is about. Currently available only inside AX.

The demo subject is a financial trading agent answering stock questions — with a dry aside that, given the previous presentation, he would not recommend building one, since they're unlikely to make you money yet. Signal surfaces issues such as traces running out without a guardrail, plus safety and intent issues. From a surfaced issue you can: hook it to your GitHub repo and create an issue there, create an evaluator so you catch that failure next time, or add it to a dataset. Evidence — traces, plus skills for Google Cloud and other logging systems — travels with the issue.

Why sandboxes are a real product decision, not a detail

He addresses the "this feels like a black box" objection head-on, and the answer is a deployment story:

"A lot of our customers don't want to connect their production systems to Anthropic … so we install in the VPC of a lot of big-name companies out there, from Uber to Booking."

— Jason Lopatecki, around 13:27

These sandboxes need to reach real infrastructure — to debug your database, they have to connect to it. Many large companies will not send those connections outbound, but are entirely comfortable installing something into their own VPC. So you can choose cloud-managed agents, Arize sandboxes, or a third party such as Daytona.

On the platform side, every run is inspectable: you can view the session that ran, download the transcript, and resume a Claude session locally to keep debugging by hand. You choose the harness, the sandbox, the driving prompt (his examples: "don't be aggressive", "look for security issues"), and the skills — pre-baked ones, your own, plus linked repos.

10The two Q&A answers worth reading twice

Q: Why not just point Claude Code at your data and let it push the PR?

His answer is not "you can't" — it's "yes, absolutely, and here's the work you're signing up for." To make it work well you need well-designed skills in the data space, and the design problems are specific:

  • Finding the right data first — e.g. a group of traces relative to one session, not everything.
  • Getting that data into the repo in a good file format — because harnesses are magical with files.
  • Giving the agent enough composable skills to actually find issues. His examples: Pyroscope skills that find memory issues; the skill knowing how to use facets in Pyroscope; being able to cohort by customer to see whether one customer is causing an issue.

The summary line: it works, but "it's not just point Claude at the data." The value Arize claims is the skill design, not the model.

Q: Where do evals come in, if you're reading traces anyway?

The answer clarifies a relationship people often get backwards. Evals — what he calls online evals — run continuously and are layered onto production traces. The eval result becomes data on the trace itself. So the agent's skills can pull both the raw trace and the aggregate eval values across many traces.

He also describes the natural lifecycle: you typically build an eval for a failure you've already seen — prompt injection attempts you're trying to catch, or a bad response pattern from before. Find a failure that keeps recurring, create an eval, and you catch it next time. And because LLM-as-a-judge runs at scale, some customers layer it across their full dataset.

11What to actually take away

The shiftFrom → To
Who observability is forA human clicking a UI → an agent reading telemetry
Who moves firstYou dig, then the agent helps → the agent digs, then you review
Your roleResponder → reviewer
How much you logAs little as a human can stand → roughly 10× more
How data reaches the agentDashboards and APIs → files in the repo, next to the code
Where the agent runsYour laptop, when you're awake → a triggered sandbox, possibly in your VPC
What's genuinely solvedNot full autonomy — the cold start
The one sentence to remember

Observability stops being a dashboard you click and becomes the smoke a system throws off for agents to read — which is exactly why you now log and trace ten times more, not less.
